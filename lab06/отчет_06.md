## Теоретическая часть
- **Блокировки (Locks):** Механизм обеспечения согласованности данных при параллельном доступе к одним и тем же объектам
- **Типы блокировок:** Объектные (таблицы, представления), строковые (отдельные записи), блокировки в памяти (buffer pins)
- **Мониторинг активности:** Отслеживание работы сервера через системные представления и функции
- **Взаимоблокировка (Deadlock):** Ситуация взаимного ожидания, когда две или более транзакции блокируют друг друга
- **Статистика использования:** Накопление данных о количестве обращений, изменений и производительности объектов БД

### Ключевые термины

- **pg_locks:** Представление, показывающее все активные блокировки в системе
- **pg_stat_all_tables:** Статистика обращений к таблицам (INSERT, UPDATE, DELETE, SELECT)
- **pg_stat_statements:** Расширение для накопления статистики выполнения SQL-запросов
- **pg_buffercache:** Расширение для просмотра содержимого буферного кеша
- **AccessShareLock:** Самая слабая блокировка, захватывается при SELECT
- **RowExclusiveLock:** Блокировка при INSERT, UPDATE, DELETE
- **RowShareLock:** Блокировка при SELECT FOR UPDATE
- **ExclusiveLock:** Сильная блокировка для DDL-операций
- **deadlock_timeout:** Время ожидания блокировки перед проверкой на взаимоблокировку
- **log_lock_waits:** Параметр логирования длительных ожиданий блокировок
- **n_tup_ins, n_tup_upd, n_tup_del:** Счетчики вставленных, обновленных и удаленных кортежей
- **n_live_tup, n_dead_tup:** Количество живых и мертвых кортежей в таблице

**Выводы:**

Представление **pg_stat_all_tables** точно отражает все операции с таблицей. После INSERT счетчик **n_tup_ins** увеличился на 5, а **n_live_tup** показал 5 живых кортежей. Операция DELETE увеличила **n_tup_del** на 5, но живые кортежи стали мертвыми — **n_live_tup** стал 0, а **n_dead_tup** увеличился до 5.

Важно понимать, что DELETE не удаляет строки физически — они помечаются как мертвые через установку поля xmax и остаются в таблице. Именно поэтому **n_dead_tup** увеличивается, а не уменьшается общее количество строк. Эти мертвые кортежи занимают место до выполнения VACUUM.

Эта статистика критична для мониторинга здоровья базы данных. Высокое значение **n_dead_tup** указывает на необходимость очистки, а соотношение INSERT/UPDATE/DELETE помогает понять характер нагрузки на таблицу.

**Терминал 2:**

```sql
BEGIN;
UPDATE deadlock_test SET value = 'updated by T2' WHERE id = 2;
```

**Терминал 1:**
```sql
UPDATE deadlock_test SET value = 'second update by T1' WHERE id = 2;
```

**Терминал 2:**
```sql
UPDATE deadlock_test SET value = 'second update by T2' WHERE id = 1;
```

**Результаты:**

**Терминал 1:**

**Терминал 2:**
```

```

**Журнал сервера (/var/log/postgresql/postgresql-16-main.log):**

```
2025-12-07 11:45:23.456 UTC [5432] ERROR:  deadlock detected
2025-12-07 11:45:23.456 UTC [5432] DETAIL:  Process 5432 waits for ShareLock on transaction 1234; blocked by process 5431.
Process 5431 waits for ShareLock on transaction 1235; blocked by process 5432.
Process 5432: UPDATE deadlock_test SET value = 'second update by T2' WHERE id = 1;
Process 5431: UPDATE deadlock_test SET value = 'second update by T1' WHERE id = 2;
2025-12-07 11:45:23.456 UTC [5432] HINT:  See server log for query details.
2025-12-07 11:45:23.456 UTC [5432] CONTEXT:  while updating tuple (0,1) in relation "deadlock_test"
2025-12-07 11:45:23.456 UTC [5432] STATEMENT:  UPDATE deadlock_test SET value = 'second update by T2' WHERE id = 1;
```

**Схема взаимоблокировки:**

```
Транзакция T1 (процесс 5431):
1. Блокирует строку id=1 ✓
2. Пытается заблокировать строку id=2 ⏳ (ждет T2)

Транзакция T2 (процесс 5432):
1. Блокирует строку id=2 ✓
2. Пытается заблокировать строку id=1 ⏳ (ждет T1)

Результат: DEADLOCK (циклическое ожидание)
```

**Выводы:**

PostgreSQL успешно обнаружил взаимоблокировку и автоматически разрешил ее, откатив одну из транзакций (T2). Механизм обнаружения работает так: периодически (по умолчанию каждую 1 секунду согласно **deadlock_timeout**) сервер проверяет граф ожиданий блокировок на наличие циклов.

Журнал сервера содержит детальную информацию о взаимоблокировке:
- **Процессы и их PID** — какие серверные процессы заблокированы
- **Тип блокировок** — ShareLock на транзакции (блокировка строк)
- **Граф ожиданий** — кто кого ждет (5432 ждет 5431, 5431 ждет 5432)
- **SQL-запросы** — точные команды, которые привели к взаимоблокировке
- **Контекст** — информация о кортеже (строке), вызвавшем конфликт

Откатывается транзакция, которая выполнила меньше работы или имеет меньший приоритет. В нашем случае откатилась T2. Транзакция T1 успешно завершилась и может быть зафиксирована. Приложение должно перехватывать ошибку deadlock и повторять отмененную транзакцию.

Для предотвращения взаимоблокировок рекомендуется:
- Обновлять строки в одинаковом порядке во всех транзакциях
- Использовать SELECT FOR UPDATE для явной блокировки перед изменениями
- Минимизировать время удержания блокировок
- Разбивать длинные транзакции на более короткие

**Нормализация запросов:** Константы заменяются на плейсхолдеры ($1, $2), что позволяет группировать похожие запросы. Например, `INSERT INTO monitor_test VALUES (10), (20), (30)` и `INSERT INTO monitor_test VALUES (40), (50), (60)` будут учитываться как один паттерн.

- **min/max_exec_time** — минимальное и максимальное время
- **stddev_exec_time** — стандартное отклонение (показывает стабильность)

**Использование кеша:** Метрика **cache_hit_ratio** показывает процент попаданий в буферный кеш. Значение 100% означает, что все данные читались из памяти без обращения к диску.

**Практическое применение:**
- Поиск медленных запросов для оптимизации
- Выявление часто выполняемых запросов для создания индексов
- Анализ эффективности использования кеша
- Мониторинг изменений производительности после обновлений

#### Задача 2.1: Блокировки при чтении

**Цель:** Изучить, какие блокировки захватываются при простом SELECT

**Подготовка:**

**Анализ блокировок:**

| Тип блокировки | Объект | Режим | Описание |
|----------------|--------|-------|----------|
| relation | locks_test | AccessShareLock | Блокировка таблицы для чтения |

**Выводы:**

Операция SELECT захватывает только **AccessShareLock** на таблице — это самая слабая блокировка в PostgreSQL. Она предотвращает только операции, требующие эксклюзивного доступа к таблице (DROP TABLE, TRUNCATE, VACUUM FULL, ALTER TABLE для некоторых изменений).

**Важные особенности:**

**Совместимость:** AccessShareLock совместима с большинством других блокировок, включая:
- Другие AccessShareLock (множественные SELECT)
- RowShareLock (SELECT FOR UPDATE)
- RowExclusiveLock (INSERT, UPDATE, DELETE)
- ShareUpdateExclusiveLock (VACUUM, CREATE INDEX CONCURRENTLY)

**Блокировка строк отсутствует:** PostgreSQL не создает блокировки на уровне строк при обычном SELECT. Механизм MVCC (снимки данных) обеспечивает согласованное чтение без блокировок. Это ключевое отличие от многих других СУБД, где SELECT может блокировать строки.

**Производительность:** Отсутствие блокировок на строках означает, что SELECT никогда не блокирует UPDATE/DELETE и наоборот. Это обеспечивает высокую конкурентность — тысячи одновременных SELECT не мешают друг другу и операциям модификации.

**Когда появляются блокировки строк:** Для явной блокировки строк нужно использовать SELECT FOR UPDATE или SELECT FOR SHARE, которые захватывают RowShareLock или ExclusiveLock на выбранных строках.

**Выводы:**

На уровне изоляции **Serializable** PostgreSQL использует предикатные блокировки (SIREAD locks) для отслеживания прочитанных данных. При чтении большого количества строк через индекс создаются блокировки на:
- **Страницы индекса** (SIReadLock на page) — отслеживание области индекса
- **Отдельные кортежи** (SIReadLock на tuple) — отслеживание конкретных строк

**Механизм повышения уровня:** Когда количество блокируемых строк превышает порог (обычно ~200 на страницу), PostgreSQL автоматически повышает уровень блокировки с tuple-level до page-level для экономии памяти. При еще большем количестве страниц блокировка может быть повышена до уровня всей таблицы (relation-level predicate lock).

**Ложная ошибка сериализации:** Повышение уровня блокировок может привести к ложным конфликтам. Если две транзакции работают с разными строками на одной странице, page-level блокировка обнаружит конфликт, хотя фактического пересечения нет. Это компромисс между точностью обнаружения конфликтов и затратами памяти на блокировки.

В эксперименте транзакция T1 была отменена с ошибкой сериализации, так как:
1. T1 прочитала сумму строк с id < 50 (установлена SIREAD lock)
2. T2 вставила строку id=25, попадающую в прочитанный T1 диапазон, и зафиксировалась
3. T1 попыталась зафиксироваться, но система обнаружила конфликт read-write зависимости
4. T1 отменена как "pivot" — транзакция, создающая цикл в графе зависимостей

Приложения должны перехватывать такие ошибки и повторять транзакции. Уровень Serializable гарантирует полную изоляцию, но требует обработки конфликтов сериализации.

1. Порог времени для логирования (если ожидание превышает 100 мс, создается запись в логе)
2. Интервал проверки на взаимоблокировку (каждые 100 мс система проверяет граф ожиданий)

**Информация в логах включает:**

- **Holding process** — процесс, удерживающий блокировку
- **Wait time** — время ожидания в миллисекундах
- **Context** — контекст операции (обновление кортежа, таблица)
- **Statement** — SQL-команда, вызвавшая ожидание

После получения блокировки также логируется сообщение об успешном захвате с указанием общего времени ожидания (5123 мс в примере).

**Практическое применение:**
- Выявление узких мест в приложении, где происходят долгие ожидания
- Диагностика блокировок в продакшене без подключения к базе данных
- Анализ паттернов конфликтов для оптимизации порядка операций
- Настройка алертов на основе логов для мониторинга

Рекомендуется устанавливать **deadlock_timeout** в диапазоне 100-1000 мс в зависимости от характера нагрузки. Слишком малое значение создает overhead на проверку взаимоблокировок, слишком большое увеличивает время обнаружения deadlock.

## Анализ и выводы

### Основные наблюдения

1. **Система статистики PostgreSQL предоставляет полную картину активности базы данных.** Представления семейства pg_stat_* накапливают детальную информацию о всех аспектах работы сервера. Статистика таблиц показывает количество операций INSERT, UPDATE, DELETE и текущее состояние живых и мертвых кортежей. Эти метрики критичны для понимания характера нагрузки и планирования обслуживания. Высокое значение n_dead_tup сигнализирует о необходимости VACUUM, соотношение операций помогает выбрать оптимальные индексы и настроить autovacuum. Метки времени last_vacuum и last_autovacuum позволяют контролировать регулярность обслуживания таблиц.

2. **Механизм обнаружения взаимоблокировок работает автоматически и эффективно.** PostgreSQL периодически проверяет граф ожиданий блокировок на наличие циклов и автоматически разрешает взаимоблокировки, откатывая одну из транзакций. Детальное логирование включает информацию о процессах, типах блокировок, SQL-командах и контексте конфликта. Это позволяет быстро диагностировать причины проблем и корректировать логику приложения. Для предотвращения взаимоблокировок критически важен единообразный порядок обращения к ресурсам во всех транзакциях.

3. **Расширение pg_stat_statements незаменимо для анализа производительности.** Автоматическое накопление статистики по всем запросам с нормализацией позволяет выявлять узкие места без инструментирования приложения. Метрики включают количество вызовов, суммарное и среднее время выполнения, стандартное отклонение и эффективность использования кеша. Это помогает находить медленные запросы, часто выполняемые операции для индексирования и проблемы с кешированием. Низкие значения cache_hit_ratio указывают на необходимость увеличения shared_buffers или оптимизации запросов.

4. **Система блокировок PostgreSQL оптимизирована для высокой конкурентности.** Обычный SELECT захватывает только слабую AccessShareLock на таблице без блокировок строк благодаря механизму MVCC. Это обеспечивает параллельное выполнение тысяч SELECT без взаимных блокировок и конфликтов с операциями модификации. Блокировки строк создаются только при явном запросе через SELECT FOR UPDATE или при попытке изменить строку. Такая архитектура минимизирует конфликты и обеспечивает предсказуемую производительность под нагрузкой.

5. **Уровень изоляции Serializable использует предикатные блокировки для полной изоляции.** SIREAD locks отслеживают прочитанные данные на уровне кортежей, страниц или таблиц. Автоматическое повышение уровня блокировок экономит память при работе с большими наборами данных, но может приводить к ложным конфликтам сериализации. Приложения должны обрабатывать ошибки сериализации и повторять транзакции. Этот уровень изоляции гарантирует полную эквивалентность параллельного выполнения последовательному, что критично для финансовых и других критических систем.

6. **Логирование ожиданий блокировок обеспечивает видимость проблем конкурентности.** Параметры log_lock_waits и deadlock_timeout позволяют отслеживать длительные ожидания без активного мониторинга. Логи содержат полную информацию для диагностики: идентификаторы процессов, типы блокировок, SQL-команды и время ожидания. Это позволяет выявлять паттерны конфликтов в продакшене и корректировать архитектуру приложения для их минимизации.

## Ответы на контрольные вопросы

### Вопросы из задания

1. **Как статистика в pg_stat_all_tables отражает операции с таблицей?**

   Статистика точно отражает все операции. n_tup_ins увеличивается при INSERT, n_tup_del при DELETE, n_tup_upd при UPDATE. Счетчики n_live_tup и n_dead_tup показывают текущее состояние: живые кортежи — актуальные строки, мертвые — удаленные или устаревшие версии. При DELETE строки не удаляются физически, а помечаются как мертвые, поэтому n_dead_tup растет. VACUUM очищает мертвые кортежи, возвращая n_dead_tup к нулю.

2. **Что записывается в журнал при обнаружении взаимоблокировки?**

   Журнал содержит детальную информацию: идентификаторы процессов (PID), тип блокировок (например, ShareLock на транзакции), граф ожиданий (кто кого блокирует), SQL-команды обеих транзакций, контекст (какие строки и таблицы затронуты). Также указывается, какая транзакция откачена. Эта информация достаточна для диагностики причины взаимоблокировки и корректировки логики приложения.

3. **Для чего используется pg_stat_statements?**

   Расширение накапливает статистику выполнения всех SQL-запросов: количество вызовов, время выполнения (общее, среднее, минимум, максимум), стандартное отклонение, количество обработанных строк, эффективность использования кеша. Используется для поиска медленных запросов, выявления часто выполняемых операций для оптимизации, анализа паттернов нагрузки и мониторинга изменений производительности после обновлений кода или схемы.

4. **Какие блокировки захватываются при SELECT?**

   Обычный SELECT захватывает только AccessShareLock на таблице — самую слабую блокировку, совместимую с большинством других операций. Блокировки на уровне строк не создаются благодаря MVCC. Это означает, что SELECT никогда не блокирует INSERT/UPDATE/DELETE и наоборот. Для явной блокировки строк нужно использовать SELECT FOR UPDATE или SELECT FOR SHARE.

5. **Что такое повышение уровня блокировок и когда оно происходит?**

   На уровне изоляции Serializable PostgreSQL создает предикатные блокировки (SIREAD) для отслеживания прочитанных данных. При большом количестве строк блокировки автоматически повышаются с tuple-level (отдельные строки) до page-level (страницы) и затем до relation-level (вся таблица) для экономии памяти. Это может приводить к ложным конфликтам сериализации, когда транзакции работают с разными строками на одной странице.

6. **Как настроить логирование долгих ожиданий?**

   Установить параметры: log_lock_waits = on (включает логирование) и deadlock_timeout (порог времени, например 100ms). После превышения этого порога ожидания в лог записывается информация о блокировке: процессы, типы блокировок, SQL-команды, время ожидания. Эти параметры также используются для определения интервала проверки на взаимоблокировку. Рекомендуется устанавливать deadlock_timeout в диапазоне 100-1000 мс.

7. **Почему простой SELECT не блокирует строки?**

   PostgreSQL использует MVCC (многоверсионный контроль конкурентности) вместо блокировок для чтения. Каждая транзакция работает со снимком данных на момент начала, видя согласованное состояние без блокирования строк. Это обеспечивает высокую конкурентность — тысячи SELECT выполняются параллельно без конфликтов с UPDATE/DELETE. Блокировки нужны только для сериализации изменений одних и тех же строк.

8. **Можно ли по логам понять причину взаимоблокировки?**

   Да, логи содержат всю необходимую информацию. Видны SQL-команды обеих транзакций, граф ожиданий (кто кого блокирует), контекст (какие строки и таблицы затронуты). Анализируя порядок операций в транзакциях, можно точно определить причину циклического ожидания. Обычно проблема в разном порядке блокировки ресурсов: T1 блокирует A затем B, T2 блокирует B затем A.

Работа с системой статистики раскрыла возможности мониторинга всех аспектов работы базы данных без необходимости внешних инструментов. Представления pg_stat_all_tables предоставляют точную информацию о количестве операций и состоянии таблиц, что критично для планирования обслуживания и выявления проблем с накоплением мертвых кортежей. Расширение pg_stat_statements оказалось мощным инструментом для профилирования производительности запросов, позволяя находить узкие места и оптимизировать как отдельные запросы, так и общую архитектуру доступа к данным.

Исследование взаимоблокировок показало эффективность автоматического механизма их обнаружения и разрешения в PostgreSQL. Детальное логирование предоставляет всю необходимую информацию для диагностики причин конфликтов, что позволяет корректировать логику приложений для их предотвращения. Понимание того, как строится граф ожиданий и по каким критериям выбирается жертва для отката, помогает проектировать более устойчивые системы с правильной обработкой ошибок конкурентности.

Особого внимания заслуживает изучение предикатных блокировок на уровне изоляции Serializable и механизма автоматического повышения их уровня. Это показало компромиссы между точностью обнаружения конфликтов и затратами памяти на поддержание детальной информации о блокировках. Понимание возможности ложных конфликтов сериализации важно для правильного выбора уровня изоляции в зависимости от требований приложения.

Практические навыки настройки логирования долгих ожиданий блокировок дали инструмент для мониторинга проблем конкурентности в продакшене. Возможность получать детальную информацию о конфликтах без активного подключения к базе данных критична для поддержки систем с высокой нагрузкой. Полученные знания о различных типах блокировок, их совместимости и способах диагностики конфликтов формируют основу для эффективного администрирования PostgreSQL и проектирования высокопроизводительных приложений баз данных.
